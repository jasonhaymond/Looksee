## 1. Decisions

| Question | Decision |
|---|---|
| UI | Fully native React Native screens for every management area (not a web view of the dashboard). |
| Push | A direct connection from the phone to the engine. No Firebase, no Expo push service, no third-party account. |
| Where it lives | `mobile/` in this repo, Expo (latest SDK), Android only. |
| Version | Same version as the engine and dashboard (lockstep); Android `versionCode` = MAJOR×10000 + MINOR×100 + PATCH. |
| Builds | The self-hosted build server (`projectRoot: "mobile"`), release APKs signed with a stored key named `looksee`. |
| Alert channel | One **Notifications** channel (the existing `web_push` type, relabelled) reaches both browsers with push on and every phone with the app (Jason, 2026-11-20; replaced a first version with a separate `app` type and per-phone choice). |

## 2. How notifications reach the phone

- A small **native Android foreground service** (Kotlin, in `mobile/modules/looksee-stream`)
  keeps one WebSocket open to `wss://<server>/api/app/stream`. It runs independently of
  the JavaScript app, so alerts arrive with the app closed, after a reboot
  (`BOOT_COMPLETED`) and after an app update.
- Android requires a permanent "Looksee is watching" notification for this kind of
  service. The app asks to be excluded from battery optimisation so Doze doesn't cut the
  connection.
- The engine **queues** every app notification per phone (`app_notifications`) and sends
  it the moment that phone is connected; the phone acknowledges each one. A phone that was
  offline (off the VPN, flight mode) receives what it missed when it reconnects — up to
  24 hours / 200 messages, so a phone left off for a week doesn't get flooded.
- Trade-off accepted with this choice: alerts only arrive while the phone can reach the
  Looksee server, and the connection uses some battery.

## 3. Signing in from the app

- Same password + mandatory two-factor flow as the dashboard (`/api/auth/login`,
  `/login/verify`), with `client: "app"`. Passkeys aren't offered in the app; the
  authenticator code or a recovery code is.
- The app gets its session token in the response body (no cookie) and sends it as
  `Authorization: Bearer …`. A header token is never sent automatically by a browser, so
  this adds no cross-site request forgery risk. The session follows the normal session
  length and idle timeout from the Security page.
- The phone is also registered as an **app device** with a separate, notification-only
  token (stored hashed). It can only receive and acknowledge notifications, so it keeps
  working after the management session expires, and can be revoked on the Security page
  (a lost phone stops receiving alerts at once). Signing out in the app removes the device.

## 4. Engine changes

- Tables `app_devices` and `app_notifications` (migration 0030, additive).
- `requireAuth` accepts a bearer session token as well as the cookie.
- `/api/app/*`: register/list/rename/remove devices, recent notifications, and the
  WebSocket stream (attached to the HTTP server in `index.ts`; the security gate's IP
  blocks and allowlist apply before the upgrade).
- `deliverText` for Notifications (`web_push`) channels sends browser push and queues one
  notification per phone, pushing it to connected ones; a test with neither a browser nor
  a phone set up reports that clearly.
- Retention prunes delivered and expired notifications.

## 5. Dashboard changes

- `lib/api.ts` gets a configurable base URL and auth header, so the app imports the same
  typed API client instead of a copy.
- Channels: browser push relabelled "Notifications (browsers and Android app)".
- Alert rules: a "Notifications" option that creates that channel on first use.
- Security page: list and revoke app devices.

## 6. The app

Native screens, sharing the dashboard's API client and check-type registry
(`dashboard/app/lib/api.ts`, `checkTypes.ts`) through Metro `watchFolders`:

- Sign-in (server address, password, two-factor or recovery code; first-time authenticator
  enrolment too).
- Overview (status counts, failing checks), Alerts (open/recent incidents).
- Locations → Sites → Endpoints → Checks, each with view/create/edit/delete.
- Check detail: status, recent results, history, run now, pause/resume, resolve, alert
  rules, edit settings with the same per-type fields as the dashboard.
- Bulk actions (manage), groups, maintenance windows, exclusion lists, channels,
  discovery, events/flows, SLA reports, logs, backups, retention, watchdog, SNMP
  templates, status pages, security (sessions, IP rules, devices, password/2FA), help.
- Settings: server, notifications (permission, battery, connection status, test),
  theme (system/light/dark), sign out.

## 7. Building

`mobile/scripts/build-android.mjs` (same shape as Readeez/Homebase): release builds only
from an approved, pushed tag; debug builds from a pushed commit. The build server's API
key and the `looksee` signing key stay where they are created; the script runs where they
live. Pre-release testing uses an x86_64 build on the emulator.

## 8. Phases

1. Engine: devices, bearer sessions, stream, `app` channel, tests.
2. Dashboard: shared API client, channel type, alert-rule option, devices on Security.
3. App core: sign-in, overview, alerts, check detail, native notification service, settings.
4. App management screens (the rest of §6).
5. Docs, build script, release builds, emulator testing.
